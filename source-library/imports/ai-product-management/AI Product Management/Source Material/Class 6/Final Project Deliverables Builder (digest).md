## Structure

Single-page tool, 2 presets (**Load Juno example**, **Start blank**), plus a unique third input mode: a **"Pull from your project repo"** live GitHub-fetch box.

### Title & framing
- Working title, one-line pitch, name + cohort, repo URL

### Module artefacts, one card per module (M1-M6)
- M1: system prompt path + Lovable prototype URL
- M2: decision matrix path + strategy one-pager path
- M3: AI PRD path (single field, confirming `prd.md` as canonical per the M3 resolution)
- M4: user flow path + trust-gap mitigations path
- M5: AWSpec path + Agent Control Panel path
- M6: eval stack path + human rubric path

### PM Execution Plan (5 fields)
Where Juno is today / What ships next (2 sprints) / What I watch (dashboards) / Red lines (numeric, not feelings) / Governance (compliance/safety/reliability/reputation)

### Build Insights (required) + showcase
Friction point, key learning, aha moment, optional Loom link

Output tabs: **Pitch (HTML, live iframe preview)**, **Repo tree** (visual file-tree with ✓/· status per artefact), **README preview**, **Self-critique** (a copyable reflection prompt, answered by the student themselves — explicitly "not in ChatGPT"), **Self-review** (6-item checklist).

## Interaction logic (notable — several new patterns, last tool in the course)

- **Live GitHub repo auto-fill**: a genuinely new mechanic not seen in any prior tool. Paste a public repo URL → the tool fetches raw files via `raw.githubusercontent.com` (probing `main` then `master` branch), parses each module's markdown into a section map, and auto-fills only *empty* fields (never overwrites existing input) by pattern-matching section headers and bullet keywords (e.g., pulls "friction"/"learning"/"aha" bullets out of a "Build Insights" section). Explicitly a "draft head start," not authoritative — the tool's own copy says "Review & edit."
- **Dual-output generation**: `pitch.html` is a fully separate, self-contained HTML document generated by string-templating (not just a styled preview of the README) — complete with its own embedded CSS, hero section, module cards, exec-plan rail, and insights row. This is the first time in the course a tool generates a *second, wholly independent HTML artifact* rather than only a markdown file.
- **Self-critique tab is explicitly not an AI-prompting step** — it's a 5-question reflection checklist ("Could a VP fund this bet from the README alone?") that the student answers themselves in their own notes, with the tool's copy explicitly noting "not in ChatGPT." This continues the course-wide pattern of positioning these builder tools' outputs as the actual deliverable, with no LLM step required to finish them.
- **File-download engine has an explicit known-limitation comment** baked into the code: the `saveFile()` function's implementation comment documents that when the tool page is embedded in a sandboxed iframe without `allow-downloads`, the browser silently blocks the save with no detectable error — so the tool deliberately avoids claiming success and instead tells the user to open the builder URL directly in a new tab if no file appears. This is a rare instance of a course tool documenting its own environment-dependent failure mode rather than hiding it.
- Repo-tree visualization renders the entire expected `juno-pm/` folder structure with live ✓ (filled) / · (missing, dimmed) status per file — the clearest "have I actually finished this" view in any tool in the course.

## Torq-rebuild notes

- **The live-repo-fetch-and-autofill mechanic is the single most sophisticated interaction pattern in the entire course** and a strong candidate for reuse in any Torq capstone/portfolio tool — the "only fill empty fields, never overwrite" rule and the section-header/bullet-keyword parsing approach are both solid, low-risk design choices worth carrying forward as-is.
- **Generating a genuinely separate `pitch.html` artifact** (not just a styled README preview) is a good pattern for any Torq capstone deliverable that needs both a machine-readable repo file and a human-presentable one-pager — consider this the reference implementation if Torq builds something similar.
- The documented iframe-download limitation is a good practice worth replicating: any Torq tool offering file downloads inside an embedded/sandboxed context should include the same kind of honest, non-claiming failure messaging rather than a generic "success" toast.
- This tool is genuinely the "keystone" artifact of the whole course — it's the only tool that reads back the six other modules' outputs rather than producing an independent one. Worth flagging to Scott: if the Torq rebuild changes any of the M1-M6 canonical file paths (a live open question per the various naming discrepancies logged elsewhere), this tool's `RF_MAP`/`RF_FILES` fetch list and the Repo-tree visualization would both need updating in lockstep, since they hardcode all 12 module-artefact paths.
