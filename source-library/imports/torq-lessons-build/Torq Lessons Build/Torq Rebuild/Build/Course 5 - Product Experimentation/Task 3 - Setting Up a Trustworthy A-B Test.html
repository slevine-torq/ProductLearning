Setting up a trustworthy A/B test

Split the traffic, change exactly one thing, measure both arms against the same rules. That isolation is the entire reason the result means anything.

Course Product Experimentation Read time ~9 min Artifact A/B Setup Checklist

Every A/B testing platform — Optimizely, Statsig, LaunchDarkly, or a homegrown tool — asks for roughly the same things, in roughly the same order. Learn the sequence once and the specific tool becomes a detail.

What makes a result trustworthy

Split your traffic in two. Hold everything constant except the one change under test. Measure both arms against the exact same primary metric and guardrails. That isolation — one variable, identical measurement — is the entire reason anyone should believe the result.

Before you touch a platform

  1. Write the hypothesis first Before you build anything, commit to a specific claim:
    Formula If we make [this change] for [this persona], then [this outcome] will follow — we'll see it as a [X%] shift in [primary metric] over [duration]. [Guardrail] stays untouched the whole time.
    Set the bar for "shippable" now. Setting it after you've seen the result isn't analysis, it's rationalization.
  2. Confirm the page or flow is instrumented The platform needs to know where to inject the test. Usually a one-time engineering task — know it's done, and who to ask, before you commit to a launch date.
  3. Build from a template if you can If you're running tests on the same pages or events repeatedly, a template turns setup from an hour into minutes — the difference between running a handful of tests a quarter and several a week.
  4. Define control and variant precisely Control is the product exactly as it exists today. The variant is your single change — nothing else. Set the traffic split on real numbers: 50/50 when you have the sample size, a smaller slice like 10/10 when risk or traffic is tight.
  5. Lock your metrics before launch Define the primary metric that decides success, and the guardrails you can't afford to move the wrong way — both before any data exists. This is your last honest chance to set the rules.
  6. Launch, then don't touch it Review every setting, publish, and leave it alone. Changing targeting, the variant, or the metrics mid-flight breaks the comparison — your two arms are no longer measuring the same thing.
Every field is a record

Name, description, target pages — none of this is bureaucracy. It's the documentation that lets you (or a teammate) understand what was tested and why, six months from now.

Key takeaways

  1. Isolation is what makes a result trustworthy. One variable, identical measurement on both arms.
  2. Write the hypothesis before you build anything. Setting the shippable bar after you see results is rationalization, not analysis.
  3. Lock your metrics before launch. This is the last point where the rules are actually neutral.
  4. Once it's live, leave it alone. A mid-flight change to targeting or metrics breaks the comparison entirely.
