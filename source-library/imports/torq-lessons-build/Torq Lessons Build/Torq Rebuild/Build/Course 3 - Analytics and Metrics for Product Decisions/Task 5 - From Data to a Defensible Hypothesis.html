From data to a defensible hypothesis

Evidence alone doesn't justify pulling engineering off something else. A hypothesis does — one specific, measurable, falsifiable bet you're willing to put your name on.

Course Analytics & Metrics for Product Decisions Hands-on ~20 min Artifact Data-Backed Hypothesis

"I want to build this" isn't a case for anything. A hypothesis is: it names the evidence, the persona, the expected change, and exactly how you'll know if you were right. This is the last gate before you ask anyone to spend real engineering time.

The formula

Template Based on [the evidence], we believe [solving this problem] for [this persona] will produce [this outcome], measured by a specific change in [this metric] — while protecting [this guardrail metric].

Notice what this does to a conversation: it moves the question from "should we build this" to "here's what we're betting on, and here's how we'll know." That's a fundamentally easier conversation to have with a skeptical stakeholder.

Know which kind of bet you're making

  • Optimizing the existing Making a known workflow better — faster, smoother, less friction. You're chasing retention or conversion, plugging a leak. Slack's addition of channel folders to tame information overload is a real example — same core product, meaningfully less friction.
  • Exploring something genuinely new Validating a need nobody's proven yet. You're chasing activation and early signs of real value, not a retention curve. Early Netflix testing DVD-by-mail against the pain of late fees is a real example of this — an unproven model at the time, not an optimization of an existing one.

Deciding which one you're doing before you start prevents the single most common mistake in this step: judging a genuinely new bet against the retention curve of a mature feature. They were never going to look the same, and shouldn't be measured the same way.

Four ways a hypothesis quietly fails

FailureWhat it looks like
Too vague"Users want a better experience" — no persona, no metric, nothing anyone could actually disagree with
Baked-in solution"Adding X will improve engagement" assumes the answer instead of testing it — you'll only ever confirm what you already believed
Not actually testable"Users will feel more confident" can't be read off a dashboard — if you can't observe it moving, it's not a hypothesis yet
Disconnected from the real goalA well-written bet that optimizes a metric nobody upstream actually cares about this quarter

Key takeaways

  1. A hypothesis is a measurable contract, not a wish. Evidence, persona, outcome, metric, and guardrail — all five, or it isn't done yet.
  2. Know whether you're optimizing or exploring before you write the metric. The two get judged by completely different standards.
  3. Watch for baked-in solutions. A hypothesis that already assumes its answer only ever confirms what you believed going in.
  4. No decision window means no real decision. Name upfront how much time or data it takes before you commit to a call.
