You've got a scoped feature and a lean PRD from the last two tasks. This lab turns that PRD into something clickable — and if you only have a few free-tier credits to work with, that's genuinely fine. A working V1 beats a polished mockup every time.

Stay in one continuous thread

If you generated your PRD in an AI chat, keep working in that same conversation rather than starting fresh. It already has your persona, metric, and scope in context — restarting throws that away for no benefit.

Two-step build

Step 1 · Hand off the PRD

Paste it into a prototyping tool with a builder hook

Open a vibe-coding tool and paste your PRD in, prefaced by a short instruction so the tool knows what to do with it:

Build a working prototype based on this PRD. Use the smart behaviors as
build rules, the functional requirements as constraints, and prioritize a
working flow over visual polish.

[paste your Task 4 PRD here]
Step 2 · Fix it by citing the PRD

Reference specific clauses, not vague feedback

When something doesn't work, don't just describe the symptom — point to the exact PRD section that's being violated:

Smart Behavior 2 isn't met — there's no field-level error shown when a
required field is left empty. Fix this specifically.

This is a transferable habit, not just a lab trick: naming the specific clause that's broken gets you a targeted fix. A vague "this feels off" gets you a guess.

Key takeaways

  1. A working V1 beats a polished mockup. The goal is proving the logic functions, not shipping something pixel-perfect.
  2. Stay in one continuous thread. Restarting the conversation throws away context you already built up for free.
  3. Cite the specific clause, not the symptom. "Fix the error handling" gets a guess; "Smart Behavior 2 isn't met" gets a targeted fix.
  4. Building the prototype tests the PRD as much as the other way around. A gap the build reveals is real signal — update the PRD, don't just patch the prototype.
