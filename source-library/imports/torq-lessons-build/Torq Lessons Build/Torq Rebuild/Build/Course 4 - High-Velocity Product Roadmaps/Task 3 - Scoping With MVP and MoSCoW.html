Scoping with MVP and MoSCoW

Prioritization tells you what to build first. Scoping tells you how much of it to actually build — and it's where most launches quietly overrun.

Course High-Velocity Product Roadmaps Read time ~8 min Artifact Scope Cut List

A "Now" item on your roadmap isn't automatically small. Left unscoped, a quick win grows a login flow, a settings page, and three edge cases nobody asked for before anyone notices scope crept out from under it.

MVP: the smallest version that's still real

A minimum viable product — a term that entered product vocabulary through Frank Robinson and was popularized by Eric Ries — is the most pared-down version of something that still delivers its core value. Two steps get you there:

  1. Define the one outcome. Pick a single high-value result this version has to deliver. Anchoring to one clear outcome is what stops feature creep before it starts.
  2. Map the shortest real path to it. List the smallest number of steps a user actually needs. If a step isn't strictly necessary to reach the outcome, it doesn't belong in this version.

The discipline here is on the experience, not the interface. Get the logic right first — polish and edge cases can wait until the core is proven.

MoSCoW: slicing the scope

Once you know the outcome, MoSCoW — a scoping method created by Dai Clegg at Oracle in the 1990s and formalized through the DSDM methodology, well predating this course — sorts every candidate requirement into one of four buckets:

BucketMeaning
Must-haveA ship-blocker — the feature doesn't function without it
Should-haveReal value, but the feature still works without it if capacity runs out
Could-havePolish for a later pass, not this one
Won't-have (now)An explicit, written exclusion — the thing that actually prevents scope creep

The kill test: for anything you're unsure about, ask "if we removed this, could the user still reach the outcome?" Yes means it's not a Must-Have, whatever it felt like a moment ago.

Worked example · Loopline's auto-suggested reply templates

Loopline picked this as a Now-lane quick win in Task 1. Scoped with MoSCoW:

  • Must-have: suggest a template based on the ticket's category — without this, the feature doesn't do anything.
  • Should-have: let an agent edit the suggestion inline before sending — high value, but a copy-then-edit workflow still functions without it.
  • Could-have: team-specific custom template libraries — a real enhancement, but next sprint's problem.
  • Won't-have (now): auto-send without agent review — explicitly excluded; removing a human from the loop entirely is a different, much bigger decision.

Key takeaways

  1. An MVP is defined by one outcome and the shortest real path to it. Everything else is a later decision, not a day-one requirement.
  2. MoSCoW is a real, decades-old framework, not an invented one. Its discipline works because the four buckets force an explicit call on everything.
  3. The kill test cuts through indecision fast. "Can they still succeed without it?" settles most Must-vs-Should debates in one question.
  4. A written Won't-Have is what actually stops scope creep. An unwritten one is just a decision waiting to be relitigated.
