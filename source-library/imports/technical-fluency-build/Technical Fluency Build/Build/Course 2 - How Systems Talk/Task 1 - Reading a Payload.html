Reading a payload

Four formats, one skill — being able to look at what a system actually sent and tell whether the field you need is in there.

Course How Systems Talk Read time ~8 min

When two systems exchange information, it arrives in one of a handful of shapes. You will never write these. You will regularly be handed one and asked whether something is possible — and being able to answer that yourself, in the meeting, is one of the cheapest wins available in this whole program.

JSON — the one you'll actually read

JSON is how systems send structured data to each other, and it's the format you'll see in ninety percent of the integration conversations you sit in. It has six types — string, number, boolean, null, array, object — and three notable absences: no comments, no date type, and no schema of its own. (JSON Schema exists, but it's a separate standard a team has to choose to adopt.)

You don't need to write it. You need to be able to look at one and answer a single question: is the field I need actually in here?

Why it matters"Can we show the customer's tier on this screen?" — a two-day question, or a two-minute one.

That's the whole return on learning to read a payload. Someone sends you a sample response, you scan it, and you either find the field or you don't. Without that, the question goes into a queue and comes back on Thursday.

XML — and what its presence tells you

XML is verbose and deeply nested, with a formal schema language (XSD) and namespaces. It's much heavier than JSON and much more rigorously specifiable.

Nobody chooses XML for a new project. So when you find it, it isn't a style preference — it's telling you the integration is old and probably standards-mandated. Which means changing it involves a partner organisation, not just a sprint.

In healthcare (HL7) and in finance, XML is usually a regulatory or industry-standard obligation. Estimating those integrations as though they're modern REST work is a classic and expensive scoping error, and it's one you can avoid just by noticing the format.

CSV and YAML — the two you'll meet outside engineering

FormatWhat it isWhere you'll meet it
CSVComma-separated values — a flat text tableUniversally supported and opens in Excel, which is why it's how business data actually moves between organizations. The default export in essentially every SaaS product
YAMLAn indentation-based configuration format, easier for humans to write than JSONConfiguration rather than data: CI/CD pipelines, Kubernetes manifests, infrastructure definitions. GitHub Actions workflows are YAML

The distinction worth holding: CSV and JSON carry data; YAML carries configuration. If someone mentions YAML, you're in a deployment or infrastructure conversation, not a data one. Course 4 picks that thread up.

CSV deserves one warning. It's flat, so it has no way to express nesting, and it has no types — everything is text until something guesses otherwise. "Can you just send me an export?" is a reasonable request that quietly loses structure, and leading zeros on account numbers are the classic casualty.

The question underneath all four

None of these formats documents itself. JSON has no built-in schema, CSV has no types, and only XML carries a formal contract by default. So the real question on any integration isn't which format is in play — it's whether anyone has written down what the fields mean.

Undocumented payloads are how integrations break silently after the consultant leaves. On an engagement judged partly on clean handoff, the absence of a documented schema is a finding you can raise in week one, and it costs nothing to check.

Tier 1 — a level deeper

Learn to read a JSON payload well enough to find a field. That single skill converts a category of question from "ask someone and wait" into "look and answer," and it's the highest-return thing in this task by a distance.

The move: next time someone shares a sample response, actually open it and find one field.

Tier 2 — the trade-off you can discuss

Format is evidence. XML means an old, probably standards-mandated integration with a partner attached. CSV means data is moving between organizations and losing structure on the way. Say what the format implies about the work, rather than about the technology.

The move: when you see XML, ask who owns the standard before you estimate the integration.

Tier 3 — strategic & risk read

The absence of a documented schema is a handoff risk with a name. Undocumented payloads break quietly after you leave, which is exactly the failure mode an engagement gets judged on later. In healthcare and finance the format is frequently a regulatory obligation, and pricing it as modern work is where estimates go wrong.

The move: treat "is there a schema?" as a due-diligence question, not a nice-to-have.

Key takeaways

  1. JSON is the one to learn to read. Six types, no comments, no dates, no built-in schema — and the field you need is either in it or it isn't.
  2. Nobody picks XML for a new project. Finding it means an old, probably standards-mandated integration with a partner organisation attached.
  3. CSV carries data; YAML carries configuration. YAML in the conversation means you're talking about deployment, not data.
  4. CSV silently loses structure and types. "Just send me an export" is where nesting disappears and leading zeros die.
  5. None of these formats documents itself. "Has anyone written down what the fields mean?" is a week-one question and a real finding.
