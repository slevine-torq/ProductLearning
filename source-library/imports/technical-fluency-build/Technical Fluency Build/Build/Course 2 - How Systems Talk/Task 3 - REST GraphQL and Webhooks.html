REST, GraphQL, and webhooks

Three ways systems talk, the mapping that makes API documentation readable without help, and one requirement everyone files as an edge case.

Course How Systems Talk Read time ~9 min

Task 2 covered what an API promises. This one covers the three shapes those promises actually take. The useful distinction is direction: with REST and GraphQL you ask, and with a webhook they tell you — which changes what you have to build and what has to be approved.

REST, and the pattern that makes documentation readable

REST organises an API around resources — nouns, addressed by URL — and uses HTTP verbs to act on them. It's stateless and cacheable, and it is the default, best-understood, lowest-risk choice.

Here is the part worth carrying out of this task:

HTTP verbWhat it doesCRUD operation
POSTMakes a new oneCreate
GETFetches itRead
PUT / PATCHChanges itUpdate
DELETERemoves itDelete

REST's verbs are CRUD. They're the same four operations wearing different names, and once you see that, most API documentation becomes readable without an engineer translating it for you. A page of endpoints stops being a wall of text and turns into a list of things you can create, read, change, or remove.

Course 3, Task 1 takes CRUD apart properly — as a permissions model and as a scoping shortcut. This table is the bridge to it, and it's worth coming back to this section when you get there.

If a client has built something bespoke instead of REST, that's worth asking about. The answer is either a real constraint or accumulated debt, and both are useful to know.

GraphQL

One endpoint, a typed schema, and clients asking for exactly the fields they want. It solves a real problem: over-fetching, where a mobile app downloads a large response to display three fields of it.

What it solvesWhat it costs
Over-fetching on mobile and complex UIsCaching gets harder — the uniform-URL trick REST relies on no longer applies
Many different clients needing different shapes of the same dataOne badly written client query can put unexpected load on the backend

Justified for a mobile-heavy product with several client applications. Over-engineering for a single web app. It adds a capability and an operational responsibility in the same decision, and the second half is the one that gets left out of the pitch.

Webhooks, and the requirement people call an edge case

A webhook inverts the direction. Instead of you asking repeatedly whether anything has happened, the provider POSTs an event to a URL you host. It's far more efficient than polling and it's how most modern integrations handle "tell me when this changes."

It also commits you to three things people forget: you have to expose a public endpoint, verify signatures so you know the event really came from the provider, and handle duplicate deliveries.

Not an edge caseWebhooks can and do arrive twice. Handling that is a requirement.

If duplicate handling isn't in the acceptance criteria, it isn't built, and you'll find out when a customer gets charged twice. Put it in writing at spec time — it costs one line then and an incident later.

Regulated client?

If you're engaged with a healthcare, aerospace & defense, or financial-services client, standing up an inbound public endpoint for webhooks likely needs a security review, a penetration test, and legal/compliance sign-off before it can move forward the way this task describes — and that review has its own queue. Assume the endpoint is an approval question before it's an engineering one, and raise it in the first design conversation rather than the sprint that needs it.

Tier 1 — a level deeper

Hold the three by direction. REST and GraphQL are you asking them; a webhook is them telling you. That alone lets you follow an integration design conversation and know which way the data is moving.

The move: learn the four REST verbs. It makes API documentation readable on your own.

Tier 2 — the trade-off you can discuss

GraphQL is the trade-off you can hold: real over-fetching relief for mobile, against harder caching and an operational responsibility somebody has to carry. On webhooks, your contribution is making duplicate handling an explicit acceptance criterion rather than an assumption.

The move: ask whether duplicate webhook deliveries are handled — before the spec is signed off.

Tier 3 — strategic & risk read

An inbound public endpoint is an attack surface and a security-review item, and in regulated environments it needs its own approval with its own lead time. GraphQL is a capability layer that someone must operate; bespoke-instead-of-REST is either a real constraint or debt, and it's worth knowing which before you price around it.

The move: schedule the security review for the inbound endpoint at the start, not at the end.

Key takeaways

  1. REST's verbs are CRUD. POST/GET/PUT/DELETE are create, read, update, delete — and seeing that makes API docs readable without a translator.
  2. REST is the default and the lowest-risk choice. Something bespoke instead is either a real constraint or accumulated debt. Ask which.
  3. GraphQL solves over-fetching and costs you caching. Justified for mobile-heavy products with many clients; over-engineering for one web app.
  4. A webhook means they call you. Which commits you to a public endpoint, signature verification, and duplicate handling.
  5. Duplicate deliveries are a requirement, not an edge case. If it isn't in the acceptance criteria it isn't built, and someone gets charged twice.
