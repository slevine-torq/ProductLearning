Backend frameworks

The four you'll actually meet, the one pattern that beats a rewrite, and why the modernization target is usually not the framework at all.

Course How Software Is Built Read time ~8 min

The backend is the logic and the data behind the screen. A framework is pre-built structure so the team doesn't write authentication, routing, and database plumbing from scratch every time. There are four you'll meet repeatedly, and the shortest way to hold them is by which language they belong to.

The four, in one line each

FrameworkLanguageCharacter
DjangoPythonBatteries included — ORM, migrations, auth, and an admin interface out of the box
Node.js / ExpressJavaScriptMinimal by design; the team assembles the rest
Spring / Spring BootJavaConvention-heavy, deep enterprise integration, very large ecosystem
.NET / C#C#Strong tooling, tight Azure and Active Directory integration

Django

Django ships with an ORM, migrations, authentication, and an auto-generated admin interface, with security defaults switched on. That admin interface is worth knowing about before you scope anything: it can eliminate weeks of internal-tool work. If a client asks for "a back-office screen" on a Django product, find out what the admin already does before that becomes a story.

It's fast to a working product, backed by a large Python hiring pool, and proven at scale — Instagram's engineering team has publicly described running Django at very large volume. The trade-off is that Django is opinionated, and fighting its conventions is expensive.

Node.js and Express — and the pattern worth recognising

Node is event-driven and non-blocking, which makes it good at handling many concurrent connections that are mostly waiting on something else. Express is deliberately minimal, so teams build their own structure on top.

One language across the whole stack simplifies hiring and allows shared code. Against that, a minimal framework means every team invents its own conventions, and onboarding an engineer into someone's bespoke Express app is slower than "we use Express" makes it sound.

The pattern to recognise: a thin API layer in front of a legacy system. It's common, it's frequently the pragmatic modernization play, and it's a far more credible recommendation than a rewrite — because it delivers value without requiring anyone to switch off the system the business runs on.

Spring, and the distinction to get right

Spring is verbose and ceremonious, and its ecosystem covers essentially every enterprise need, with a deep and experienced hiring pool. It is rarely the wrong choice for a large regulated organization. It's also what's actually running under most of Torq's client industries.

Which sets up the distinction that matters most in this task. When a client talks about modernizing, Spring itself is usually not the target:

  • "You're on Spring — that's the thing holding you back." "Is what's slowing you down the framework, the monolithic architecture around it, or not having CI/CD?"

Nine times out of ten it's the second or third. Getting that distinction right in a scoping conversation is the difference between a credible recommendation and an expensive one nobody will fund. Course 3 covers the architecture question and Course 4 covers CI/CD.

.NET and C# — the vendor-concentration conversation

Cross-platform since .NET Core, strongly typed, excellent tooling, and tightly integrated with Azure and Entra ID. If a client is already committed to Microsoft, .NET reduces integration friction substantially.

And it deepens an already-deep single-vendor relationship. Both of those are true at once, and the useful thing you can do is name both when a client asks whether to standardize further. Efficiency and lock-in arrive in the same purchase; a client who hears only the first half will be surprised later.

ORM — and a cheap diagnostic

An Object-Relational Mapper lets engineers work with database rows as objects in their own language instead of hand-writing SQL. It removes enormous boilerplate and prevents whole classes of injection bug.

It also hides what queries are actually running — which is the usual root cause of "the app got slow as the data grew." When a client reports performance degrading with scale, the ORM's generated queries are a common and cheap-to-investigate culprit. Naming that as a diagnostic step before anyone proposes re-architecture is a genuinely useful contribution, and it costs an afternoon rather than a program.

One level up:

Whether a client standardizes further on a single vendor's platform is usually a CIO-level call, and how it gets scoped into a phased SOW is usually an AD/Director one rather than yours. Knowing how the decision gets made is what lets you feed it good input now — and make it yourself later.

Tier 1 — a level deeper

Hold them by language: Django is the Python one, Express the JavaScript one, Spring the Java one, .NET the Microsoft one. That's genuinely enough to follow a backend conversation and know which team you're talking to.

The move: if it's Django, ask what the built-in admin already covers before scoping a back-office screen.

Tier 2 — the trade-off you can discuss

Two are yours. Separating the framework from the architecture and the delivery process, so a modernization conversation aims at the right thing. And raising the ORM as a first diagnostic when performance degrades with scale, which is cheap to check and frequently right.

The move: "framework, architecture, or CI/CD?" before agreeing what modernization means.

Tier 3 — strategic & risk read

Vendor concentration is the .NET conversation, and naming both halves is what makes you useful rather than agreeable. The thin-layer-in-front-of-legacy pattern is often the phase-one that makes a longer program fundable. And a Python dependency chain in a regulated environment becomes a security-scanning obligation someone has to own.

The move: propose the thin layer as phase one, not the rewrite as phase never.

Key takeaways

  1. Hold the four by language. Django/Python, Express/JavaScript, Spring/Java, .NET/Microsoft.
  2. Spring is rarely the modernization target. The monolithic architecture around it and the absence of CI/CD usually are.
  3. A thin API layer in front of legacy beats a rewrite. More credible, more fundable, and it doesn't require switching anything off.
  4. .NET buys integration efficiency and vendor lock-in together. Name both halves, especially when asked whether to standardize further.
  5. Check the ORM before anyone proposes re-architecture. Hidden generated queries are the usual cause of "it got slow as we grew."
