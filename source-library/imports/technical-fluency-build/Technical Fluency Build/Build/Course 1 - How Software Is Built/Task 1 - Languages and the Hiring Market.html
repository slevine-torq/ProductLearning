Languages, and the hiring market attached

The four things every web product is built from, what each one tells you about the team that built it, and one small tell worth not making.

Course How Software Is Built Read time ~8 min

A language is never only a technical choice. It comes with a hiring market, a body of existing code, and a set of things that are cheap or expensive to change later. You don't need to write any of it. You need to know what a client has told you when they name one.

First, the small tell

HTML and CSS are not programming languages. They describe structure and appearance; they don't express logic. Calling them programming languages in an engineering room is a minor thing that gets noticed, and it's the kind of error that makes people quietly discount the rest of what you say.

The useful framing: HTML is the content and its meaning, CSS is how it looks, JavaScript is what happens when you interact with it. Every web product you'll ever see on an engagement is those three, plus whatever is behind them.

HTML — where accessibility actually lives

HTML is declarative markup. The part that matters to you is semantic HTML: using the right element for the job, so a heading is a heading and a button is a button. Screen readers and search engines both depend on that.

Which leads to the read that's worth having. A page can look immaculate and still be unusable with a screen reader, because accessibility is determined by the markup underneath rather than by the visual design on top. If a client's product has never had an accessibility audit, that's a finding you can raise on your own authority.

CSS — and the question that changes every UI estimate

CSS controls appearance through cascading rules. Modern layout is Flexbox and Grid; modern styling is usually organised as a design system — a set of named tokens for color, spacing, and type that components draw from.

Here is why you care. "It's just CSS" is true for changing one color. It is false for a layout change on a product with no design system, where the same change becomes an audit of every page. Those two situations produce estimates that differ by an order of magnitude, and they sound identical in a status meeting.

Ask earlyIs there a design system — and does the team actually use it?

Ask before you agree to any visual-change estimate, not after. A design system is a capital asset; its absence is a recurring tax on every future UI change, and that makes it a legitimate line item in a transformation business case rather than an engineering preference.

JavaScript and TypeScript

JavaScript runs in every browser, and through Node.js it runs on servers too. It has the largest developer population of any language, which cuts both ways: hiring risk is low, and code-quality variance is high, because the barrier to entry is low.

TypeScript is a type layer on top of JavaScript. You write types, a compiler checks them, and then they vanish — what actually runs is JavaScript. That's the whole idea.

What it buysWhat it costs
Plain JavaScriptNothing to configure; anyone can contribute immediatelyIn a large codebase, a real and compounding drag on velocity — the compiler catches nothing for you
TypeScriptWhole categories of bug caught before the code runs; the code documents itselfAdding types to an existing untyped codebase is its own project, not an incremental tidy-up

"Is the codebase typed?" is one of the fastest reads available on engineering maturity. It's a single question, an engineer will answer it in four words, and it correlates with how safely a new team can pick the work up after Torq leaves. On an engagement judged partly on clean handoff, that matters more than it first appears.

Regulated client?

If you're engaged with a healthcare, aerospace & defense, or financial-services client, accessibility is likely a legal exposure and a procurement requirement rather than a quality goal — and a remediation program needs legal/compliance review, a longer approval cycle, and scheduling early rather than at the end. Public-sector work in particular tends to make conformance a contractual condition, not a backlog item.

Tier 1 — a level deeper

Know which of the four you're hearing about, and don't call HTML or CSS a programming language. That alone keeps you out of the two most common mistakes a non-engineer makes in a stack conversation.

The move: when someone names a language, ask what part of the product it runs.

Tier 2 — the trade-off you can discuss

Two trade-offs are yours to raise. The design-system question, because it decides what a UI change costs. And the typing question, because retrofitting types onto a large untyped codebase is a project someone has to fund, and pretending it's incremental is how it never happens.

The move: "does a design system exist?" before any visual-change estimate leaves the room.

Tier 3 — strategic & risk read

Design-system investment is one of the more defensible line items in a transformation case, because the return is measurable: every subsequent UI change gets cheaper. Missing accessibility is exposure with a legal shape. An untyped codebase raises the cost and risk of the handoff you're contractually promising.

The move: price the absence of a design system as a recurring tax, not a one-off fix.

Key takeaways

  1. A language is a choice with a hiring market attached. Naming one tells you about the team and the code as much as the technology.
  2. HTML and CSS are not programming languages. They describe structure and appearance; calling them otherwise is a small, costly tell.
  3. Accessibility is decided in the markup, not the design. A beautiful page can be unusable, and no audit is a finding.
  4. "Is there a design system?" changes every UI estimate. One token change versus an audit of every screen, and both sound the same in a meeting.
  5. "Is the codebase typed?" is the fastest maturity read you have. Four words to ask, and it predicts how cleanly you can hand off.
