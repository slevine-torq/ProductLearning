The languages behind the logic

What's running under a Fortune 500 client's core systems, what mobile really commits you to, and the one language worth learning yourself.

Course How Software Is Built Read time ~8 min

Task 1 covered what a browser runs. These five are what sits behind it: the core business systems, the data work, and the mobile apps. In Torq's client industries you will meet Java far more often than anything fashionable, and knowing what that implies is worth more than knowing twenty framework names.

Python — wherever the data is

Interpreted, dynamically typed, with an enormous standard library. Python owns data science and machine learning through pandas, NumPy, PyTorch, and scikit-learn, and it's exceptionally fast to develop in.

The read: if a client is doing anything serious with data or AI, Python is in the stack. Often it's sitting in a team the main engineering org doesn't manage — an analytics group, a data science function, someone's notebook. That has dependency-management and security-scanning implications the client may not have planned for, and it's worth finding before someone else does.

Python is slower at raw computation than Java. That rarely matters, and occasionally matters enormously. It's an engineer's call, not yours.

Java — what's actually under the client

Statically typed, compiled to bytecode, running on the JVM. Verbose by design, with mature tooling and a deep hiring pool. This is the language under most Fortune 500 core systems in Torq's industries — banking, airlines, insurance, healthcare.

Two things follow, and they pull in opposite directions. A large Java monolith is usually where the technical debt lives, and modernizing it is a multi-year program rather than a refactor. At the same time it has decades of proven operation and an enormous replacement cost behind it.

  • "You should rewrite this off Java." "What would have to be true for this to stay where it is for another five years?"

"Rewrite it" is almost never the credible recommendation, and offering it early is a reliable way to be excluded from the serious conversation. Course 3 covers the architecture question properly; for now, note that the target is usually the process around the code rather than the language it's written in.

Swift and Kotlin — and what mobile commits you to

Swift is Apple's language for iOS, compiled and memory-safe, with SwiftUI as the current UI framework. Kotlin is Google's preferred Android language since 2019 — statically typed, far less boilerplate than Java, and fully interoperable with it.

What it buysWhat it commits you to
Swift (iOS)Best performance and same-day access to new iOS capabilitiesMac hardware, an Apple developer account, and App Store review in your release timeline — with no SLA you control
Kotlin (Android)Modern language on a codebase that can migrate from Java file by fileStill a separate codebase and separate team from iOS

Those three Swift commitments are schedule risks that simply don't exist for a web deliverable, and they get omitted from plans constantly. If your engagement has an iOS release in it, App Store review is a dependency with someone else's hand on it.

Kotlin migration is one of the rare modernizations you can genuinely do incrementally, because Java and Kotlin interoperate. So if a client cites "we're migrating to Kotlin" as the reason a roadmap is slow, that's worth probing gently — the migration itself doesn't usually require stopping.

SQL — the one to learn yourself

SQL is declarative: you describe the result you want and the database works out how to get it. Dialects differ between vendors, but the core transfers.

It is, straightforwardly, the highest-return technical skill available to a consultant. Being able to write your own query removes a dependency on someone else for every question you have, and most of the questions you have on an engagement are simple ones. You do not need to be good at it to benefit.

The organizational read matters too. When every business question routes through a two-week data-team queue, that's a transformation finding with a cost you can quantify — and it's the kind of finding that opens a conversation about how the client operates, not just what it runs.

One level up:

Whether a core-system modernization gets scoped as a phased SOW, a strangler-pattern program, or left alone entirely is usually an AD/Director call rather than yours. Knowing how the decision gets made is what lets you feed it good input now — and make it yourself later.

Tier 1 — a level deeper

Know which of these five you're hearing and roughly what each one is for: Python for data, Java for the core system, Swift for iOS, Kotlin for Android, SQL for asking the data a question. That's enough to follow a stack conversation without reconstructing it afterward.

The move: learn enough SQL to answer one of your own questions this month.

Tier 2 — the trade-off you can discuss

The mobile conversation is the one you'll own most often. Native buys performance and immediate platform access, and commits you to two teams plus a review process outside your control. Say the commitment out loud when the release date is being set, not when it slips.

The move: put App Store review on the plan as a dependency with a name, not a buffer.

Tier 3 — strategic & risk read

A Java core system carries a replacement cost that makes "rewrite" non-credible and makes the surrounding process the real target. Unmanaged Python in an analytics team is an unbudgeted security-scanning obligation. A data-team queue is an operating-model finding, which is a larger and better-paid conversation than a tooling one.

The move: quantify the queue before proposing anything that replaces it.

Key takeaways

  1. Java is what's under most Fortune 500 core systems in Torq's industries. Deep hiring pool, decades of operation, enormous replacement cost.
  2. "Rewrite it" is almost never credible. The modernization target is usually the process around the code, not the language.
  3. Serious data or AI work means Python is in the stack. Often outside the main engineering org, and often unscanned.
  4. Native mobile commits you to review cycles you don't control. App Store review is a dependency with a name, not a buffer.
  5. SQL is the highest-return skill on this list for you personally. You don't have to be good at it to stop waiting on other people.
